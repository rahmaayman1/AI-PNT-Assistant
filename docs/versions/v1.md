# v1 - Original baseline detector

**Status:** kept unchanged as the reference baseline. Its originally reported results were found to be
inflated by the evaluation setup (see [Re-evaluation](#re-evaluation-what-the-reported-numbers-really-mean)).
Do not cite the original headline numbers as performance claims.

Artifacts: `models/detector.pkl`, `models/scaler.pkl`, `models/threshold.txt`, `models/satellite_baselines.csv`.
Development notebook: `notebooks/Network_PNT.ipynb`.

---

## 1. What v1 is

An unsupervised anomaly detector for GPS spoofing, trained on normal readings only.

```
TEXBAT channel observables (per satellite, 5 Hz)
    -> filtering (valid flag, channel status >= 5)
    -> rolling features (window = 10 samples, per scenario and satellite)
    -> per-satellite C/N0 z-score (baseline from normal training rows)
    -> StandardScaler -> Isolation Forest (200 trees, seed 42)
    -> anomaly score -> percentile threshold (20) -> flag
    -> hysteresis (3 of the last 5 flags) -> GPS or network source
```

### Features (5)

| Feature | Meaning |
|---|---|
| `cn0_zscore_per_satellite` | C/N0 normalized against each satellite's own baseline mean/std |
| `cn0_rolling_std` | Rolling std of C/N0 (10 samples) |
| `cn0_diff` | First difference of C/N0 |
| `doppler_rolling_std` | Rolling std of Doppler (10 samples) |
| `doppler_diff` | First difference of Doppler |

### Training and threshold

- Training data: normal rows (label 0) of `cleanStatic`, `ds2` and `ds3` (`ds7` excluded on purpose).
- Per-satellite baseline: mean and std of C/N0 from the normal training rows.
- Threshold: the 20th percentile of the anomaly scores of the normal training rows, so by construction
  about 20% of normal training rows are flagged.
- `contamination` of the Isolation Forest is irrelevant for the final decision, because the threshold is
  taken from the percentile of the scores.

### Data sizes

| Scenario | Normal rows | Attack rows |
|---|---|---|
| cleanStatic | 30,030 | 0 |
| ds2 | 6,020 | 23,531 |
| ds3 | 6,650 | 23,461 |
| ds7 | 9,100 | 21,770 |

Total normal rows used for training and testing: 42,700.

## 2. Development journey

Each step was driven by a diagnostic finding.

1. **Raw features (C/N0, Doppler + rolling stats):** recall 0.17, nearly all attacks missed.
2. **Threshold tuning alone:** best recall 0.53, so the problem was not the threshold.
3. **Per-scenario breakdown:** identical recall (0.17) on ds2 and ds3 despite very different visual
   separation, pointing to a shared underlying issue.
4. **Root cause:** satellites have very different natural C/N0 levels (about 36 to 53 dB-Hz). Raw C/N0 made
   the model confuse "naturally weak satellite" with "anomalous satellite".
5. **Raw values removed, relative features only:** recall stayed at 0.17. In ds2 the attack causes a brief jump
   followed by a long stable period at a new level, which relative features alone do not capture.
6. **Per-satellite z-score for C/N0:** recall rose to 0.33. Normalizing, not removing, the absolute value was the fix.
7. **Doppler z-score tested and dropped:** no improvement, because Doppler drifts continuously with satellite motion.
8. **Final feature set + percentile tuning:** recall rose from 0.33 (percentile 5) to 0.91 (percentile 20)
   with precision 0.94.

Lesson that survived the re-evaluation: defining "normal" **per satellite** was the most important improvement.

## 4. Re-evaluation: what the reported numbers really mean

The notebook was re-examined cell by cell and the results were re-computed under a leakage-free protocol
(see [v2](v2.md)). The conclusion is **not** classical overfitting: the gap between training and test
normal rows was about zero. The numbers were optimistic because of how they were measured.

### 4.1 The test split leaked

The normal rows were split with a random 70/30 row split (`train_test_split`, `random_state=42`). Samples are
0.2 s apart and every rolling feature shares 9 of its 10 values with the previous sample, so a test row has a
near-identical neighbour in the training set. With such a split the false-positive rate on the test normals
equals the nominal one by construction.

| Split | FPR at percentile 5 | FPR at percentile 20 |
|---|---|---|
| Random rows (as in v1) | 0.050 | 0.199 |
| Temporal (last 30% of each recording, 2 s gap) | 0.046 | 0.255 |

The v1 test FPR matched the nominal rate almost exactly, which is what a leaking split produces. The temporal
split gives a higher false-positive rate in the wider-threshold regime. This is one split on short recordings, so
it is an indication, not a precise number.

### 4.2 Choices were made on the test set

- The percentile threshold was selected by scanning values and reading recall/precision on the test set.
- The feature set (v1 to v4) was selected by looking at test recall.

So the final numbers are not an unbiased estimate: the test data influenced the model.

### 4.3 Precision depended on class balance

The test set contained 12,810 normal rows and 46,992 attack rows, i.e. **78.6% attack**. Precision depends
on this ratio, so precision 0.94 mostly reflects the composition of the test set. (On ds7, 70.5% of the rows
are attack and precision was 0.84.) Metrics that do not depend on the ratio (AUC, recall at a fixed
false-positive rate) are more informative.

### 4.4 Labels and detector were not independent

The ds2/ds3 attack onsets were found from the C/N0 signal, and C/N0 is also the main detection feature. High recall
on ds2 is therefore partly expected.

### 4.5 What the threshold means operationally

Percentile 20 flags about 20% of normal rows. With a "3 of the last 5 flags" rule, a false switch would occur in
about 5.8% of windows **if flags were independent**; real flags are correlated in time, so this is only an
illustration of the order of magnitude.

## 5. v1 under the leakage-free protocol

Protocol: baseline and model fitted without the tested scenario, threshold-free metrics.

| Experiment | Result |
|---|---|
| ds2, scenario seen in training (normal part) | AUC 0.901, recall 0.32 at 5% FPR |
| ds2, scenario unseen | AUC 0.898, recall 0.31 at 5% FPR |
| ds3, seen | AUC 0.846, recall 0.24 at 5% FPR |
| ds3, unseen | AUC 0.840, recall 0.23 at 5% FPR |
| ds7, unseen | AUC 0.705, recall 0.10 at 5% FPR (0.20 at 10%) |
| ds2 / ds3 / ds7 without the C/N0 z-score | AUC 0.632 / 0.594 / 0.529 |

Findings:

- Seen and unseen results are almost the same: the model does not memorize scenarios, which is why "overfitting"
  is not the right description.
- The model is essentially a detector of the C/N0 level relative to each satellite's normal level; without the
  z-score it is close to chance.
- At 5% false positives v1 catches about 31% (ds2) and 23% (ds3) of attacks, far below the originally reported 0.91.

## 6. Code-level observations

These come from reading the code; their effect on the numbers was **not** measured.

- `main.py` reads the source in 50-row chunks and calls the feature builder on each chunk, so the rolling windows
  restart with every chunk. v2 keeps per-satellite state across chunks.
- The hysteresis in `decision_engine.py` votes over consecutive rows. Rows are ordered per satellite, so five
  consecutive rows can come from five different satellites instead of five consecutive moments.
- Rows of satellites that are missing from the training baseline are dropped silently, so an attacker that spoofs a
  PRN absent from the baseline would not be flagged.
- The notebook and `model.py` are equivalent for the final decision (the threshold comes from the percentile, so the
  `contamination` setting does not matter).

## 7. Known limits carried into later versions

- Calibration gap with GNSS-SDR: 100% false-positive rate when applied to observables from a software receiver
  (z-score -0.5 to -3.7 for most satellites, -16.3 for one weak satellite).
- ds7-type attacks are only partially detectable from C/N0.
- Single receiver, static scenarios, three attack recordings.

How v2 addresses the evaluation problems and the feature problem: [v2.md](v2.md).
